# 12 기술 아키텍처

## 전제

- Godot 4로 만든다. [확정] 처음에는 Flutter로 정했으나 3D 표현의 위험이 커서 바꿨다.
- 안드로이드 먼저, 이후 아이폰. [확정]
- 2.5D로 표현한다. [확정] 처음에는 3D로 정했으나 화면 샘플을 비교한 뒤 바꿨다.

개발 PC에는 Godot 4.7.2가 설치되어 있고, 시험 단말기는 갤럭시 S20+(안드로이드 13)다.

잠실 판을 플레이하는 장면이 개발 PC와 단말기에서 돈다. 정지 장면(벽돌 277개, 건물 3,031채, 그림자)은 갤럭시 S20+에서 초당 61프레임이 나왔다(2026-11-24). 그 뒤 셀마다 노드를 하나씩 두는 구조로 바꾸고 나무와 강 풍경을 더한 플레이 장면도 같은 단말기에서 초당 61프레임이었다. 공이 하나일 때 화면에 표시된 값을 한 번 읽은 것이다. 공 여러 개와 파편이 들어간 상태는 재지 않았다.

## 엔진 재비교

Godot으로 확정한 뒤 Unity와 다시 비교했고, Godot을 유지하기로 했다. [확정]

처음에 Unity를 권한 이유는 3D 연출과 성능의 위험이었다. 그 뒤 두 가지가 바뀌었다. 표현이 2.5D로 정해졌고, 잠실 실측으로 장면의 크기(건물 1,616개, 셀 277개)가 가볍다는 것을 알았다. 그 이유가 대부분 사라졌다.

| 항목 | Unity 6 | Godot 4 | 이 게임에서의 무게 |
|---|---|---|---|
| 2.5D 고정 카메라, 단순한 건물 | 충분 | 충분 | 차이 없음 |
| 파편 수백 개의 물리 연출 | 강함 | 가능. 기기에서 확인 필요 | 터짐 연출에서만 중요 |
| 판정 코드의 속도 (봇 수천 판) | C#이라 빠름 | GDScript는 느림. C#은 모바일 내보내기가 실험 단계 | 중간. 봇 판수를 줄이거나 오래 돌리면 됨 |
| 광고, 결제 | 공식 지원 | 커뮤니티 플러그인 (AdMob, 결제 모두 있음) | 수익화 방식에 따라 큼 |
| 비용과 조건 | 연 매출과 투자 20만 달러 미만 무료 | 조건 없이 무료 | 작음 |
| 설치와 계정 | 허브, 계정, 라이선스 필요 | 실행 파일 하나 | 작음 |
| 코드 중심 작업, AI와의 협업 | 장면과 설정이 에디터에 묶임 | 프로젝트 파일이 전부 텍스트, 명령줄 실행 | 큼. 이 저장소는 AI 하네스로 작업한다 |
| 자료와 사례 | 가장 많음 | 적지만 늘고 있음 | 중간 |

초안 작성자의 권장은 **Godot 유지**다. 남은 차이 중 이 프로젝트에 가장 크게 걸리는 것이 작업 방식이고, 그 점에서 Godot이 맞다.

Unity로 돌아갈 이유가 되는 경우는 둘이다. 광고 수익이 사업의 중심이어서 여러 광고망을 묶어 써야 하는 경우, 그리고 M0에서 터짐 연출이 기준 기기에서 30fps에 못 미치는 경우다.

표의 근거(2026-11-24 검색): Unity Personal의 매출 기준과 스플래시 화면 선택 사항은 [Unity 가격 안내](https://unity.com/products/pricing-updates), Godot C#의 모바일 지원 상태는 [Godot 4.2 C# 플랫폼 현황](https://godotengine.org/article/platform-state-in-csharp-for-godot-4-2/), 플러그인은 Godot 에셋 라이브러리의 [AdMob](https://www.godotengine.org/asset-library/asset/2063)과 [Godot IAP](https://www.godotengine.org/asset-library/asset/4627)에서 확인했다. Godot C#의 최신 버전 상태와 각 플러그인의 유지 관리 상태는 확인하지 못했다.

## 표현 방식

2.5D로 그린다. [확정] 판정은 평면에서 하고, 화면은 입체로 그리되 카메라를 고정한다.

같은 잠실 데이터를 세 방식으로 그려 비교했다([서울-1 잠실](stages/seoul_jamsil.md)의 화면 샘플 링크).

| | 2D | 2.5D | 3D |
|---|---|---|---|
| 뜻 | 위에서 똑바로 내려다본 평면 | 입체로 그리되 카메라는 고정, 판정은 평면 | 원근 카메라, 실제 높이 |
| 읽기 쉬움 | 가장 좋다 | 좋다 | 먼 쪽이 작아지고 높은 건물이 도로와 공을 가린다 |
| HP 표현 | 색이나 숫자로 따로 | 건물 높이로 읽힌다 | 건물 높이로 읽힌다 |
| 무너지는 연출 | 약하다 | 좋다 | 가장 좋다 |
| 조준 | 정확하다 | 정확하다 | 원근 때문에 어렵다 |
| 성능 부담 | 가장 작다 | 중간 | 가장 크다 |

2.5D를 고른 이유:

- 이 판 크기에서는 건물이 화면에서 아주 작다. 20m짜리 건물이 5픽셀쯤이다. 3D로 공들여 그려도 차이가 잘 보이지 않는다.
- 완전한 2D는 지도 그림과 구분이 안 되고, 카타르시스의 핵심인 "무너져 쏟아지는" 장면이 약해진다.
- 2.5D는 높이를 HP로 읽게 해 주면서 도로를 가리지 않는다. 샘플에서 58도로 내려다봤을 때 통로가 가려지지 않았다.
- 카메라가 고정이라 평소 부담이 작고, 터짐 같은 순간에만 카메라를 움직여 3D의 효과를 쓸 수 있다.

구현은 3D 장면에 직교 카메라를 고정하는 방식을 제안한다. 2D 엔진으로 입체를 흉내 내는 방식이 아니다. 아주 높은 건물은 화면에서 길어지지 않도록 높이를 눌러 그린다(샘플은 60m를 넘는 부분을 45%로 줄였다). [제안]

## 판정과 렌더의 분리 [제안]

표현 방식이 정해지지 않았어도 개발을 시작할 수 있도록, 그리고 나중에 표현을 바꿀 수 있도록 둘을 나눈다.

```
입력 ──→ sim (2D 판정) ──→ 상태 ──→ render (화면 표현)
                │                              
                └──→ 이벤트 (타격, 파괴, 터짐) ──→ render, audio, haptic
```

- sim은 Godot의 장면 노드와 렌더링에 의존하지 않는 순수한 코드로 둔다.
- sim은 고정 시간 간격(초당 120회)으로 돈다. 같은 입력이면 같은 결과가 나온다.
- render는 sim의 상태를 읽고 이벤트를 받아 그리기만 한다. sim의 상태를 바꾸지 않는다.
- 파편, 먼지 같은 연출용 물리는 render 쪽에 두고 판정에 영향을 주지 않는다. 여기에는 Godot의 3D 물리를 쓸 수 있다.

이렇게 하면 얻는 것:

- 봇이 화면 없이 sim만 돌려 스테이지를 검증할 수 있다. Godot은 화면 없이 실행하는 모드가 있다.
- 입력 기록만으로 리플레이와 점수 검증이 된다.
- 판정 로직을 단위 테스트할 수 있다.

## 판정 구현 [미결정]

게임의 판정은 원(공)과 다각형(셀)의 충돌이 전부다.

- 직접 구현: 결정성과 성능을 완전히 통제한다. 터널링 방지를 직접 처리해야 한다. 권장.
- Godot 2D 물리: 빨리 시작할 수 있다. 같은 입력에 같은 결과가 나오는지, 화면 없이 빠르게 돌릴 수 있는지 확인해야 한다.

판정에 쓰는 언어(GDScript, C#)도 여기서 함께 정한다. 봇이 수천 판을 돌려야 하므로 속도가 기준이다.

## 주요 모듈

모듈은 `src/` 아래에 같은 이름의 폴더로 둔다. 전체 구조는 저장소 [README](../README.md)에 있다.

| 모듈 | 책임 |
|---|---|
| sim | 시간 진행, 충돌, 반사, 중력 |
| entities | 공, 패들, 셀, 건물, 랜드마크의 상태 |
| items | 아이템 정의와 효과 적용 |
| catharsis | 코어 충전, 터짐, 도미노의 판정 |
| stage | 스테이지 파일로 판 구성, 클리어와 실패 판정 |
| scoring | 점수, 콤보, 별 |
| render | 화면 표현, 카메라, 연출 |
| input | 터치를 패들 명령으로 변환 |
| data | 스테이지 파일과 세이브의 모델, 읽기와 쓰기 |
| meta | 해금, 도감, 과제 |
| ui | 화면과 HUD |

## 성능 예산 [제안]

기준 기기는 3년 전 중급 안드로이드폰으로 잡는다. 구체적인 모델은 M0에서 정한다.

| 항목 | 목표 |
|---|---|
| 프레임 | 평소 60fps, 터짐 중 최소 30fps |
| 판 위의 셀 | 최대 300개 |
| 블록 위에 올리는 것 | 블록당 큼직한 것 1~4개와 나무 몇 그루. 블록마다 몸통과 윗것을 한 노드로 묶는다. 깨질 때 함께 사라져야 하기 때문이다 |
| 판정 대상 공 | 최대 40개 |
| 연출용 파편 | 동시에 최대 300개. 1~2초 뒤 파티클로 바꾸거나 없앤다 |
| 나무와 꾸밈 | 최대 5,000개. 같은 모양을 한 번에 그리는 방식으로 묶는다 (잠실 샘플은 나무 약 2,000그루) |
| 스테이지 로딩 | 2초 이내 |
| 스테이지 파일 | 개당 500KB 이내 (잠실 실험 데이터는 약 230KB) |

터짐 연출은 파편을 미리 쪼개 두고, 판정과 무관한 파편은 단순한 탄도 운동으로 처리한다.

## 밸런스 값

속도, HP, 점수 같은 값은 코드에 쓰지 않고 데이터 파일에 둔다. 스테이지별 값은 `design.json`에, 전역 값은 별도 밸런스 파일에 둔다.

## 테스트 [제안]

- sim, scoring, items, catharsis의 판정은 단위 테스트한다.
- 스테이지 파일은 로딩 테스트와 봇 검증을 거친다.
- 화면은 주요 흐름만 확인한다.

## iOS 대비

- 플랫폼 전용 코드를 쓰지 않는다. 필요하면 인터페이스 뒤에 둔다.
- 햅틱, 세이브 경로, 광고와 결제처럼 플랫폼마다 다른 부분은 한곳에 모은다.
- 광고와 결제는 Godot에 공식 지원이 없어 커뮤니티 플러그인을 써야 한다. 수익화 방식([09 진행과 메타](09_progression_meta.md))을 정할 때 함께 확인한다.
