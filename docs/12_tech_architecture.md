# 12 기술 아키텍처

## 전제

- Flutter로 만든다. 안드로이드 먼저, 이후 아이폰. [확정]
- 3D로 표현한다. [확정]

현재 개발 환경은 Flutter 3.35.7, Dart 3.9.2다.

## 가장 큰 기술 위험: Flutter의 3D

Flutter는 2D UI 프레임워크이고 3D 게임 렌더링은 주력 영역이 아니다. 이 프로젝트에서 기술적으로 가장 불확실한 부분이므로 먼저 검증한다.

렌더링 방식은 정해지지 않았다. [미결정]

| 안 | 방식 | 장점 | 위험 |
|---|---|---|---|
| A | Flame + 의사 3D. 2D 캔버스에 건물을 기울인 시점으로 직접 그린다 | 안정적이고 자료가 많다 | 조명, 그림자, 파편 연출에 한계 |
| B | flutter_scene. Impeller 위의 3D 렌더러 | 실제 3D. Flutter 안에서 해결 | 실험 단계였다. 안정 채널 지원 여부와 성능을 확인해야 한다 |
| C | flame_3d | Flame과 통합 | 실험 단계였다 |
| D | 네이티브 3D 엔진을 Flutter에 삽입 | 3D 성능 확실 | 플랫폼별 연동 비용. Flutter를 쓰는 이점이 줄어든다 |

B와 C의 현재 성숙도는 이 문서를 쓰는 시점에 확인하지 못했다. [14 로드맵](14_roadmap.md)의 M0에서 A와 B를 같은 장면으로 만들어 비교하고 정한다.

## 프레임워크 재검토 [미결정]

Flutter 대신 게임 엔진을 쓰는 방안을 검토 중이다. 이 게임에 필요한 것을 기준으로 비교한다.

| 필요한 것 | Unity | Godot 4 | Flutter |
|---|---|---|---|
| 모바일 3D 렌더링 | 검증됨 | 가능. 저사양 기기는 확인 필요 | 실험 단계 |
| 지도 데이터로 메시를 실행 중에 생성 | 가능 | 가능 | 렌더러에 따라 다름 |
| 파편 수백 개의 물리 연출 | 강함 | 가능 | 직접 구현 |
| 판정 코드를 엔진 없이 실행 (봇, 테스트) | C# 라이브러리로 분리 가능 | 헤드리스 실행 | 순수 Dart로 가능 |
| 광고, 결제 SDK | 공식 지원 | 커뮤니티 플러그인 | 공식 지원 |
| 안드로이드와 아이폰 동시 지원 | 지원 | 지원 | 지원 |
| 비용 | 매출 기준 이하 무료 | 무료 (MIT) | 무료 |
| 코드 중심 작업, 버전 관리 | 에디터 의존이 있다 | 프로젝트 파일이 텍스트 | 좋음 |

초안 작성자의 권장은 **Unity**다. 이 게임의 위험은 3D 연출과 성능에 몰려 있고, 그 부분에서 가장 검증된 선택이기 때문이다. 스테이지를 데이터에서 생성하므로 에디터에서 손으로 장면을 짜는 일이 적어 에디터 의존의 단점도 줄어든다.

Godot은 엔진이 가볍고 무료이며 코드 중심으로 작업하기 좋다. 광고와 결제 연동을 직접 챙길 수 있고 저사양 기기 성능을 먼저 확인한다면 좋은 선택이다.

위 표의 엔진별 현황은 최신 버전으로 확인하지 않았다. 결정 전에 확인한다.

프레임워크가 바뀌어도 이 문서의 아래 내용(판정과 렌더의 분리, 성능 예산)과 다른 기획 문서는 그대로 유효하다. 바뀌는 것은 저장소의 폴더 구조와 이 문서의 구현 세부다.

## 판정과 렌더의 분리 [제안]

렌더러가 정해지지 않았어도 개발을 시작할 수 있도록, 그리고 나중에 렌더러를 바꿀 수 있도록 둘을 나눈다.

```
입력 ──→ sim (2D 판정, 순수 Dart) ──→ 상태 ──→ render (3D 표현)
                │                              
                └──→ 이벤트 (타격, 파괴, 터짐) ──→ render, audio, haptic
```

- `lib/game/sim`은 Flutter를 import하지 않는다.
- sim은 고정 시간 간격(초당 120회)으로 돈다. 같은 입력이면 같은 결과가 나온다.
- render는 sim의 상태를 읽고 이벤트를 받아 그리기만 한다. sim의 상태를 바꾸지 않는다.
- 파편, 먼지 같은 연출용 물리는 render 쪽에 두고 판정에 영향을 주지 않는다.

이렇게 하면 얻는 것:

- 봇이 화면 없이 sim만 돌려 스테이지를 검증할 수 있다.
- 입력 기록만으로 리플레이와 점수 검증이 된다.
- 판정 로직을 단위 테스트할 수 있다.

## 물리 [제안]

게임의 판정은 원(공)과 다각형(셀)의 충돌이 전부다. 범용 물리 엔진 없이 직접 구현하는 방안과 Forge2D(Box2D의 Dart 이식)를 쓰는 방안이 있다.

- 직접 구현: 결정성과 성능을 완전히 통제한다. 터널링 방지를 직접 처리해야 한다.
- Forge2D: 빨리 시작할 수 있다. 결정성과 공 수십 개일 때의 성능을 확인해야 한다.

M0에서 Forge2D로 시작하고 문제가 보이면 직접 구현으로 바꾼다. sim 내부의 선택이라 바깥에는 영향이 없다.

## 주요 모듈

폴더 구조는 저장소 [README](../README.md)에 있다.

| 모듈 | 책임 |
|---|---|
| `game/sim` | 시간 진행, 충돌, 반사, 중력 |
| `game/entities` | 공, 패들, 벽돌, 블록, 랜드마크의 상태 |
| `game/items` | 아이템 정의와 효과 적용 |
| `game/catharsis` | 코어 충전, 터짐, 도미노의 판정 |
| `game/stage` | 스테이지 파일로 판 구성, 클리어와 실패 판정 |
| `game/scoring` | 점수, 콤보, 별 |
| `game/render` | 3D 표현, 카메라, 연출 |
| `game/input` | 터치를 패들 명령으로 변환 |
| `data` | 스테이지 파일과 세이브의 모델, 읽기와 쓰기 |
| `meta` | 해금, 도감, 과제 |
| `ui` | 화면과 HUD |

## 성능 예산 [제안]

기준 기기는 3년 전 중급 안드로이드폰으로 잡는다. 구체적인 모델은 M0에서 정한다.

| 항목 | 목표 |
|---|---|
| 프레임 | 평소 60fps, 터짐 중 최소 30fps |
| 판 위의 벽돌 | 최대 250개 |
| 판정 대상 공 | 최대 40개 |
| 연출용 파편 | 동시에 최대 300개. 1~2초 뒤 파티클로 바꾸거나 없앤다 |
| 스테이지 로딩 | 2초 이내 |
| 스테이지 파일 | 개당 500KB 이내 |

터짐 연출은 파편을 미리 쪼개 두고, 판정과 무관한 파편은 단순한 탄도 운동으로 처리한다.

## 밸런스 값

속도, HP, 점수 같은 값은 코드에 쓰지 않고 데이터 파일에 둔다. 스테이지별 값은 `design.json`에, 전역 값은 별도 밸런스 파일에 둔다.

## 테스트 [제안]

- sim, scoring, items, catharsis의 판정은 단위 테스트한다.
- 스테이지 파일은 로딩 테스트와 봇 검증을 거친다.
- 화면은 주요 흐름만 위젯 테스트한다.

## iOS 대비

- 플랫폼 전용 코드를 쓰지 않는다. 필요하면 인터페이스 뒤에 둔다.
- 렌더링 방식을 고를 때 iOS에서도 같은 코드로 도는지를 조건에 넣는다.
- 햅틱, 세이브 경로처럼 플랫폼마다 다른 부분은 `core`에 모은다.
