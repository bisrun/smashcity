# 13 데이터 파이프라인

OSM 데이터에서 스테이지 파일을 만드는 과정을 정의한다. 모든 항목은 [제안]이다.

## 원칙

- 스테이지는 개발 중에 미리 만들어 앱에 넣는다. 앱이 실행 중에 OSM을 내려받아 변환하지 않는다.
- 변환은 자동이고, 그 위에 기획자가 손으로 얹는다. 자동 결과를 직접 고치지 않는다. 다시 변환하면 사라지기 때문이다.

## 흐름

```
OSM 추출 → 변환 (stage_baker) → map.json ─┐
                                          ├→ 검증 (봇) → 앱에 포함
              기획자 작성 → design.json ───┘
```

## 변환 단계

`tools/stage_baker`가 수행한다. 변환 규칙은 [03 지도 변환 규칙](03_map_conversion.md)을 따른다.

| 단계 | 하는 일 |
|---|---|
| 1. 추출 | 지정한 범위의 도로, 건물, 물, 공원, 철도, 시설을 가져온다 |
| 2. 투영 | 위도와 경도를 미터 단위 평면 좌표로 바꾸고 스테이지 방향에 맞게 회전한다 |
| 3. 통로 | 큰 도로의 중심선에 공 지름 기준 폭을 주어 통로 면을 만든다 |
| 4. 블록 | 통로로 둘러싸인 영역을 블록으로 만든다 |
| 5. 셀 | 블록을 작은 길로 쪼개 셀을 만든다. 너무 큰 셀은 건물 기준으로 다시 나누고, 너무 작은 셀은 이웃에 합친다 |
| 6. 속성 | 층수로 HP를 정하고, 시설 태그를 아이템 후보로 기록한다 |
| 7. 점검 | 공이 낄 만큼 좁은 통로, 닿을 수 없는 블록, 벽돌 수 범위를 확인한다 |
| 8. 출력 | `map.json`을 쓴다 |

도구의 구현 언어는 정하지 않았다. 지오메트리 라이브러리가 풍부한 Python을 권한다. 봇 검증은 앱과 같은 판정 코드를 써야 하므로 Dart로 돌린다.

## 스테이지 파일

`assets/stages/<도시>/<스테이지>/` 아래에 두 파일을 둔다. 예: `assets/stages/seoul/jamsil/`.

**map.json**: OSM에서 자동으로 만든 것.

| 항목 | 내용 |
|---|---|
| `bounds` | 원본 범위, 회전각, 판의 실제 가로와 세로 |
| `corridors` | 통로 면, 도로 등급 |
| `blocks` | 블록 윤곽, 속한 셀 목록 |
| `cells` | 셀 윤곽, HP, 속한 건물 목록 |
| `buildings` | 건물 윤곽, 층수, 층수가 추정값인지 여부, OSM ID, 건물 용도, 속한 셀 |
| `water` | 물 면 |
| `bridges` | 다리 면 |
| `parks` | 공원 면, 나무 위치 |
| `stations` | 역 위치, 노선 |
| `pois` | 시설 위치, 태그, 속한 셀 |

**design.json**: 기획자가 쓴 것.

| 항목 | 내용 |
|---|---|
| `paddle` | 기준선 위치, 패들 폭 |
| `ball` | 속도 단계, 시작 위치 |
| `physics` | 중력(0~1) |
| `goal` | 목표 유형과 값 |
| `landmark` | 대상 셀, HP, 약점 방향 |
| `items` | 아이템의 자리(지도 좌표)와 종류. 그 자리의 셀에 아이템이 들어간다 |
| `walls` | 깨지지 않는 벽. 감쌀 자리, 범위, 구멍의 방향과 폭 |
| `core` | 코어 영역, 충전량, 터짐 범위, 공 개수 |
| `domino` | 대상 셀, 쓰러지는 방향 조건 |
| `overrides` | 셀별 HP 덮어쓰기, 파괴 불가 지정 |
| `scoring` | 기준 시간, 랜드마크 점수 |
| `imagined` | 상상 아이템의 종류와 위치, 빈 셀을 무엇으로 채울지, 나무와 꾸밈의 배치 규칙 |
| `look` | 색 팔레트, 시간대 |

세부 스키마는 M0에서 첫 스테이지를 만들며 정한다.

## 검증

1. 로딩 테스트: 두 파일이 서로 맞는지 확인한다. `design.json`이 가리키는 셀이 `map.json`에 있어야 한다.
2. 봇 시뮬레이션: [07 스테이지 레벨링](07_stage_leveling.md)의 검증 절차를 따른다.

## OSM 원본 관리

- 원본 추출본은 저장소에 넣지 않는다. `tools/stage_baker/.cache/`에 두고 git에서 제외한다.
- 어느 날짜의 데이터로 만들었는지 `map.json`에 기록한다. OSM은 계속 바뀌므로 재현하려면 날짜가 필요하다.
- `design.json`은 대상을 그 안의 건물 OSM ID로 가리킨다. 지도를 다시 변환해도 연결이 유지되도록 하기 위해서다. 그래도 건물이 합쳐지거나 삭제되면 깨질 수 있으므로 로딩 테스트로 잡는다.

## 라이선스

OSM 데이터는 ODbL을 따른다.

- 앱 안에 "© OpenStreetMap contributors"를 표기해야 한다([10 UX와 UI](10_ux_ui.md)).
- OSM을 가공한 데이터베이스를 배포하면 그 데이터베이스에 같은 라이선스로 공개할 의무가 생길 수 있다. `map.json`이 여기에 해당할 가능성이 있다.
- 그래서 수작업 기획 내용과 상상으로 더한 것을 `design.json`으로 분리한다. `map.json`에는 OSM에서 온 것만 둔다. 공개 의무가 생기더라도 `map.json`만 대상이 되도록 하려는 것이다.

이 해석은 법률 검토를 거치지 않았다. 출시 전에 확인한다.
